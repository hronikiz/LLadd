## 1. Цель работы

Цель данной лабораторной работы — научиться обслуживать Web-серверы, работающие в Docker-контейнерах: разворачивать многоконтейнерное приложение (Apache + PHP-FPM + MariaDB), организовывать автоматическое резервное копирование средствами cron, а также анализировать журналы (логи) работы сервисов, выводимые в стандартные потоки STDOUT/STDERR.

---

## 2. Архитектура решения

Решение состоит из четырёх контейнеров, объединённых общей Docker-сетью `internal`:

| Контейнер | Образ | Назначение |
|---|---|---|
| httpd | httpd:2.4 | Веб-сервер Apache, точка входа, проксирует *.php на php-fpm |
| php-fpm | php:7.4-fpm | Исполнение PHP-кода WordPress |
| mariadb | mariadb:10.8 | База данных CMS WordPress |
| cron | debian:latest | Резервное копирование сайта и БД, очистка старых бэкапов, мониторинг |

Все контейнеры взаимодействуют по имени сервиса (например, `mariadb`), что обеспечивается общей определённой в `docker-compose.yml` сетью `internal`.

---

## 3. Подготовка окружения

Создана структура папок проекта:

```
additional/
├── database/        — данные MariaDB
├── files/
│   ├── httpd/        — конфигурация Apache
│   └── cron/
│       └── scripts/  — скрипты резервного копирования
├── site/wordpress/   — исходный код CMS WordPress
└── backups/
    ├── mysql/        — дампы базы данных
    └── site/         — архивы файлов сайта
```

В папку `site/wordpress/` распакован дистрибутив CMS WordPress, скачанный с официального сайта.

## 4. Контейнер Apache HTTP Server

Базовый конфигурационный файл `httpd.conf` был извлечён из временного контейнера `httpd:2.4` командой `docker cp`, после чего отредактирован:

- раскомментированы модули `mod_proxy.so`, `mod_proxy_http.so`, `mod_proxy_fcgi.so`;
- добавлено перенаправление *.php-запросов в контейнер php-fpm через `ProxyPassMatch`;
- задан индексный файл `index.php`;
- параметр `DocumentRoot` изменён на `/var/www/html`.

`Dockerfile.httpd` копирует отредактированный конфиг в образ `httpd:2.4` и обновляет пакеты.

---

## 5. Контейнер PHP-FPM

`Dockerfile.php-fpm` собирается на основе образа `php:7.4-fpm` с установкой библиотек для работы с изображениями (GD) и базой данных (mysqli, pdo_mysql), необходимых для корректной работы WordPress.

---

## 6. Контейнер MariaDB

Контейнер `mariadb:10.8` хранит данные в volume `./database/:/var/lib/mysql`, что обеспечивает сохранность базы данных независимо от пересоздания контейнера. Параметры базы данных (имя, пользователь, пароль) заданы переменными окружения в `docker-compose.yml`.

## 9. Сервис резервного копирования (cron)

Контейнер cron собирается на основе образа `debian:latest` с установленными пакетами `cron` и `mariadb-client`. В нём реализованы четыре сценария:

| Скрипт | Назначение |
|---|---|
| `01_alive.sh` | Сообщение `alive <username>` — индикатор работоспособности cron |
| `02_backupsite.sh` | Архивирование `/var/www/html` в `/var/backups/site/` |
| `03_mysqldump.sh` | Дамп базы данных через mysqldump, сжатие gzip, сохранение в `/var/backups/mysql/` |
| `04_clean.sh` | Удаление файлов бэкапов старше 30 дней (`find -mtime +30 -delete`) |

Скрипты выводят сообщения в `/proc/1/fd/1` и `/proc/1/fd/2` — это файловые дескрипторы STDOUT и STDERR процесса с PID 1 внутри контейнера (то есть самого cron), что позволяет видеть сообщения скриптов командой `docker logs`, согласно стандартной практике логирования в контейнерах.

### Итоговое расписание crontab

Согласно заданию, расписание задач приведено к следующему виду:

```
  *  *  *  *  * /scripts/01_alive.sh > /dev/null
  0  1  *  *  * /scripts/03_mysqldump.sh > /dev/null
  0  0  *  *  1 /scripts/02_backupsite.sh > /dev/null
  0  2  *  *  * /scripts/04_clean.sh > /dev/null
```

| Поле расписания | Смысл |
|---|---|
| `0 1 * * *` | Каждый день в 01:00 — резервная копия базы данных CMS |
| `0 0 * * 1` | Каждый понедельник (5-е поле = 1) в 00:00 — резервная копия директории CMS |
| `0 2 * * *` | Каждый день в 02:00 — удаление резервных копий старше 30 дней |

## 11. Ротация логов

В отличие от классической установки на выделенном сервере, в данной конфигурации Apache HTTP Server не пишет журналы в файлы — они перенаправлены в стандартные потоки вывода контейнера. Согласно директивам в файле `files/httpd/httpd.conf`:

- журнал общего назначения (`CustomLog`) выводится в `/proc/self/fd/1` — то есть в STDOUT контейнера;
- журнал ошибок (`ErrorLog`) выводится в `/proc/self/fd/2` — то есть в STDERR контейнера.

Оба журнала можно просматривать командой `docker logs additional-httpd-1`, без необходимости обращаться к файловой системе контейнера. Такой подход — стандартная практика для контейнеризированных приложений, упрощающая централизованный сбор логов внешними средствами (например, ELK-стеком или Docker logging drivers).

## 12. Ответы на контрольные вопросы

### 12.1. Зачем необходимо создавать пользователя системы для каждого сайта?

Отдельный системный пользователь для каждого сайта обеспечивает изоляцию: процессы веб-сервера и PHP одного сайта не получают доступ к файлам другого сайта на той же машине. Это ограничивает последствия взлома или ошибки в одном сайте — скомпрометированный процесс работает с правами своего пользователя и не может читать или изменять данные других сайтов, файлы которых принадлежат другим системным учётным записям. Также это упрощает учёт ресурсов (квоты на диск, лимиты процессов) и администрирование — резервное копирование, права доступа и логирование становятся индивидуальными для каждого сайта.

### 12.2. В каких случаях Web-сервер должен иметь полный доступ к папкам (папке) сайта?

Полный доступ (чтение, запись, а где требуется — выполнение) обычно нужен к тем директориям, куда сайт или CMS должны самостоятельно записывать данные во время работы: папкам загрузок (uploads), кэша, временных файлов, логов приложения, а также директориям, куда CMS устанавливает обновления, темы или плагины (как в случае WordPress — каталог `wp-content`). К остальным частям сайта (например, к основному коду движка и конфигурационным файлам) на боевом сервере обычно достаточно прав только на чтение — это снижает риск, что взломанный или ошибочно работающий процесс веб-сервера изменит исполняемый код сайта.

### 12.3. Что означает команда `chmod -R 0755 /home/www/anydir`?

Команда рекурсивно (`-R`, то есть для самой папки и всех файлов и подпапок внутри неё) устанавливает права доступа `0755` для каталога `/home/www/anydir`. Права `0755` в восьмеричной записи расшифровываются так:

| Владелец (owner) | Группа (group) | Остальные (others) |
|---|---|---|
| 7 = rwx (чтение, запись, выполнение) | 5 = r-x (чтение, выполнение) | 5 = r-x (чтение, выполнение) |

Таким образом, владелец получает полный контроль над файлами и папками, а группа и все остальные пользователи системы могут только читать файлы и заходить в папки (выполнять/просматривать содержимое директорий), но не могут изменять или удалять их содержимое.

### 12.4. В скриптах shell каждая команда оканчивается строкой `> /proc/1/fd/1`. Что это означает?

`/proc/1/fd/1` — это специальный путь в виртуальной файловой системе `/proc`, который указывает на файловый дескриптор номер 1 (стандартный вывод, STDOUT) процесса с PID 1. Внутри контейнера именно процесс с PID 1 является главным процессом (в данном случае — cron), и именно его STDOUT/STDERR попадают в журнал, видимый через команду `docker logs`. Поскольку задачи cron выполняются как отдельные дочерние процессы со своим собственным STDOUT, который никуда не перенаправляется по умолчанию, перенаправление вывода скрипта именно в `/proc/1/fd/1` (а не просто в обычный stdout скрипта) гарантирует, что сообщения попадут в общий лог контейнера и будут видны при просмотре `docker logs`, а не потеряются в STDOUT процесса крон-задачи.
